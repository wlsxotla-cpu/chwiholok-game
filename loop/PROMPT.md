# 루프 지시서 (PROMPT)

이 문서는 자율 개발 루프의 매 바퀴마다 새로 열리는 세션에게 그대로 주어지는 지시입니다.
이전 바퀴와의 대화 기록은 없습니다 — 이 문서와 아래에서 가리키는 파일들이 유일한 기억입니다.

---

## ① 합격 기준 (한 문장)

이번 바퀴에서 바꾼 것을 직접 실행해서 확인했을 때, 의도한 대로 동작하고 지금까지
유지해 온 퀄리티(무협 톤, 판정 범위와 이펙트가 정확히 일치, 절차적 생성 아트의
한계 안에서 최선)에서 벗어나지 않는가 — **통과하지 못했다면 커밋하지 말고,
`docs/STATUS.md`의 "막힌 것 / 확인이 필요한 것"에 왜 막혔는지만 남긴다.**

---

## ② 먼저 읽을 문서

작업을 시작하기 전에 아래 순서대로 읽으세요.

1. `docs/DESIGN.md` — 무엇을 만드는가
   - 어디까지 읽을지: 전체. 짧고 거의 안 바뀌는 문서이므로 매 바퀴 전체를 읽는다.
2. `docs/STATUS.md` — 어디까지 했고 다음은 뭔가
   - 어디까지 읽을지: "마지막 갱신"부터 "막힌 것 / 확인이 필요한 것"까지의
     최신 섹션만. 맨 아래 "이전 기록"은 지금 상황과 무관하므로 건너뛴다.
3. `docs/feedback/INBOX.md` — 가장 먼저 처리해야 할 지시
   - 어디까지 읽을지: "처리 대기" 섹션 전체. "처리 완료"는 이미 끝난 일이므로
     건너뛴다. 처리 대기가 비어 있지 않다면 이번 바퀴는 무조건 그 항목부터 다룬다.

---

## ③ 규칙과 근거

아래에 규칙을 적을 때는 반드시 "왜"를 함께 남기세요. 이유 없는 규칙은 시간이 지나면 지켜지지 않습니다.

- 규칙: 그림/아이콘/이펙트는 Python(PIL 등) 같은 도구로 절차적으로 생성해라.
  좌표를 손으로 하나하나 찍어서 인물이나 복잡한 형태(예: 동적 포즈의 캐릭터
  일러스트)를 그리려 하지 마라.
  - 왜: 실제로 시도해봤을 때, 손으로 좌표를 지정해 복잡한 형태를 그리면
    외곽선이 뭉개지고 비례가 무너져서 퀄리티가 안 나왔다. 아이콘처럼 단순한
    도형(원형 배지, 직선, 다각형)은 괜찮지만, 그 이상은 실패한다. 복잡한
    일러스트가 필요하면 만들지 말고 STATUS.md에 남겨서 사람에게 넘긴다.

- 규칙: 공격 이펙트(시각 효과)의 크기·범위는 실제 판정(데미지가 들어가는 범위)과
  반드시 정확히 일치시켜라. 눈대중으로 비슷하게 맞추지 마라.
  - 왜: 실제로 이펙트가 판정 범위보다 거의 2배 크게 표시되던 버그가 있었다.
    이펙트가 실제 판정과 다르면 플레이어가 "맞았는데 왜 안 죽지" 혹은
    "안 맞았는데 왜 맞았지"라고 느끼고, 이건 코드 리뷰로는 안 보이고 직접
    실행해서 눈으로 비교해야만 드러난다.

- 규칙: 새로운 바이너리 에셋(.png/.wav/.mp3 등)을 추가하면, 그걸 참조하는
  스크립트를 쓰기 전에 헤드리스 임포트를 두 번 연속 돌려라.
  - 왜: Godot은 새로 추가된 에셋을 처음 임포트할 때 "리소스 로더 없음" 에러를
    내고, 그 스크립트를 참조하는 오토로드가 컴파일에 실패한다. 두 번째
    패스에서는 정상화된다. 이건 알려진 패턴이라 매번 새로 헤매지 말고 그냥
    두 번 돌리면 된다.

- 규칙: 전투/이동/충돌에 관련된 로직은 전부 `_physics_process`를 써라.
  `_process`를 섞어 쓰지 마라.
  - 왜: 실제로 새 무기(오비트) 로직을 `_process`로 짰다가, 이 게임의 나머지
    전투 로직(플레이어 이동, 몹 AI, 충돌 판정)이 전부 `_physics_process`
    기준이라 타이밍이 어긋나서 데미지가 거의 안 들어가는 문제가 있었다.

- 규칙: 조합/진화로만 얻어야 하는 특수 아이템(예: 두 무기를 합쳐서 나오는
  결과물)은 일반 선택 풀과 같은 테이블에 넣지 마라. 별도로 분리하고, 일반
  선택 로직에서 명시적으로 제외해라.
  - 왜: 실제로 같은 테이블에 넣었다가, 조건(재료 두 개를 만렙까지 찍어야 함)
    없이 레벨업 화면에 바로 뽑힐 수 있는 버그가 있었다. 조건부로 얻어야 하는
    것과 자유 선택 가능한 것은 자료구조 단계에서부터 분리해야 한다.

- 규칙: 스폰 속도·확률·수치처럼 여러 값이 곱해져 상호작용하는 값을 바꿨다면,
  코드 리뷰만으로 끝내지 말고 실제로 짧게라도 돌려서(시뮬레이션 혹은 직접
  플레이) 결과를 확인해라.
  - 왜: 실제로 몬스터 밀도를 올렸을 때, 숫자 하나하나는 합리적으로 보였지만
    실제로 돌려보니 초반 난이도가 감당 안 되게 어려워지는 걸 뒤늦게 발견했다.
    여러 수치가 곱해지는 상호작용은 계산으로 예측하기 어렵다.

## ④ 한 바퀴 도는 순서

1. **읽기** — 위 ②의 문서들을 순서대로 읽는다.
2. **하나만 만들기** — 이번 바퀴에 끝낼 작업을 하나만 고른다. 여러 개를 동시에 벌이지 않는다.
3. **실행해서 눈으로 확인** — 코드를 실행하고 결과를 직접 확인한다. 코드가 도는 것과 의도대로 동작하는 것은 다른 문제다.
4. **커밋** — 아래 ⑤의 규칙에 따라 커밋한다.
5. **STATUS.md 갱신** — 무엇을 했고, 다음엔 뭘 할지 `docs/STATUS.md`에 남긴다.

---

## ⑤ 커밋 순서 규칙

- 검사를 통과하면, 화면을 보기 **전에** 일단 커밋한다.
- 한 바퀴는 도중에 멈출 수 있다. 멈춘 자리에 커밋이 없으면 그 작업은 사라진다.

---

## ⑥ 검사와 QA

- 화면이 있는 것을 만들면, 실행해서 스크린샷을 찍고 그 이미지를 직접 읽어라. 코드가 도는 것과 화면이 괜찮은 것은 다른 문제다.
- 같은 지적이 두 번 나오면 규칙으로 올리고, 기계가 잴 수 있는 규칙이면 검사로 만들어 둬라. 한 번 겪은 고장을 두 번 겪지 않는다.
